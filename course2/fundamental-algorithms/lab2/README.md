## Сборка и проверка

Программы собираются в папку `build/`.

```sh
make                              # gcc -std=c99 -Wall -Wextra -Wpedantic -g ... -lm  ->  build/lab2_taskN
make test                         # все тесты
make memcheck                     # все тесты под valgrind
bash run_tests.sh 1               # тесты одного задания
bash run_tests.sh --memcheck 1    # то же под valgrind
./build/lab2_task1 -r hello       # запуск одной программы
make clean                        # удалить build/
```

Файл тестов (`tests/tests_taskN.txt`): первая значимая строка `program: <имя>`, далее блоки, разделенные пустой строкой.
Поля блока: `args` (аргументы; аргумент с пробелами - в кавычках), `input` (строка стандартного ввода),
`out` / `outre` (строка stdout; `outre` - регулярное выражение POSIX ERE), `err` (строка stderr), `code` (код возврата),
`file` / `fout` (файл, который должна создать программа, и его строки). Строки сравниваются целиком, без учета пробелов в конце.
Пути в тестах (`tests/data/...`) указаны относительно папки лабораторной (где лежат `Makefile` и `run_tests.sh`): `run_tests.sh` запускает программы из нее.

## Проверка утечек и ошибок памяти

`make memcheck` запускает каждый тест из `tests/tests_task*.txt` (включая ветви с ошибочным вводом) под

```sh
valgrind -q --leak-check=full --show-leak-kinds=definite,indirect,possible \
         --errors-for-leak-kinds=definite,indirect,possible --track-origins=yes --error-exitcode=99
```

Тест считается непройденным, если valgrind завершился с кодом 99 (ошибка доступа к памяти или утечка); в конце выводится итог по каждому заданию.

Результат проверки (Ubuntu в WSL 2, gcc 15.2.0, valgrind 3.26.0): сборка с `-Werror` без предупреждений, все тесты пройдены,
valgrind - 0 ошибок и 0 утечек. Та же проверка выполняется GitHub Actions при каждом push (`.github/workflows/check.yml` в корне репозитория).
На Windows (сборка `zig cc`, Universal CRT) те же тесты проходят; утечки дополнительно проверены Dr. Memory 2.6.0 и heob 4.2.

## Замечания по заданиям

**Задание 1, флаг `-c`.** По условию генератор засевается функцией `srand`, поэтому используется стандартная пара
`srand`/`rand`. Формула `rand` в стандарте не задана: при одном и том же seed порядок склейки на Linux (glibc) и
Windows (UCRT) различается, а на одной системе всегда повторяется. Поэтому тесты проверяют результат `-c`
регулярным выражением (любая перестановка строк). Строки обрабатываются побайтно (`char`): для текста в UTF-8
длина `-l` - это число байт.

**Задание 2.** Запуск: `lab2_task2 <входной файл> <-a|/a|-d|/d> <выходной файл>`. Строка файла - `id имя фамилия зарплата`;
любая неправильная строка - ошибка с номером строки, выходной файл тогда не создается. id - целое от 0 до `LLONG_MAX`
(разбирается вручную, `-1` и `1.5` - ошибки), имя и фамилия - только латинские буквы, зарплата - цифры с необязательной
дробной частью через точку. Компаратору `qsort` нельзя передать eps (прототип задан, глобальные переменные запрещены),
поэтому при чтении зарплата один раз переводится в целое число единиц eps (`salary_to_units`, eps = 10^-6), а компаратор
сравнивает целые числа: зарплаты, равные с точностью eps, равны, и порядок транзитивен (прямое `fabs(a - b) < eps` в
компараторе этого не дает). Отсюда предел зарплаты ~9.22e12. Фамилии и имена сравниваются без учета регистра, при
совпадении - с учетом (`Ivanov` раньше `ivanov`). Последний признак - текст зарплаты: так выходной файл одинаков на любой
системе. Зарплата пишется в выходной файл тем же текстом, что во входном (без округления). Вход и выход - один файл
(в том числе `./in.txt` и `in.txt`) - ошибка: сравниваются файлы (`stat` / `_fullpath`), а не строки путей.

**Задание 4.** Задача о рюкзаке решается точно. Файлы больше вместимости и файлы с важностью 0 отбрасываются;
если оставшиеся помещаются все вместе, берутся все (так обрабатывается огромная вместимость, например 10^18).
Иначе выбирается способ, которому нужно меньше всего работы: таблица по размеру (`n * (capacity + 1)` клеток),
таблица по важности (`n * (сумма важностей + 1)`) или полный перебор (`2^n`, при n <= 22). Таблицы ограничены
10^7 клеток; если ни один способ не проходит, выводится ошибка `the task is too big`, а не попытка выделить
гигабайты памяти. Числа - `long long`, разбираются вручную с проверкой переполнения (`-1`, `+5`, `1.5` - ошибки).
Имена любой длины (строки читаются через `realloc`), уникальность имен проверяется сортировкой (`qsort`).
Ошибка выводится, только если не помещается в `long long` важность самого ответа.

**Задание 8.** Числа хранятся строками и складываются поразрядно (`add_in_base`), поэтому их длина не ограничена
встроенными типами. Функция с переменным числом аргументов `sum_in_base(&rez, base, kolvo, ...)` принимает числа
как `char *`. При запуске с аргументами командной строки числа прибавляются к сумме по одному
(`sum_in_base(&rez, base, 2, summa, argv[i])`), так как количество аргументов `...` должно быть известно при компиляции.
На входе цифры-буквы допускаются в любом регистре, в ответе - заглавные; ведущие нули удаляются.

**Задание 10.** Переразложение выполняется «на месте» многократным делением на `(x - a)` по схеме Горнера
(`horner_shift`, около n²/2 операций, одно выделение памяти под ответ). Функция с переменным числом аргументов
`polynomial_reexpand(eps, a, &g, n, f0, ..., fn)` принимает коэффициенты как `double` (литералы нужно писать `1.0`, а не `1`).
Режим с аргументами командной строки вызывает вариант с массивом `reexpand_array` (тот же алгоритм), так как число
аргументов `...` должно быть известно при компиляции. Коэффициенты, меньшие `eps` по модулю, считаются нулем
(убирает шум округления вида 1e-18). Ответ проверяется подстановкой: f(x) и g(x - a) сравниваются в точках x = -2..2
с относительной точностью `|f - g| <= eps * (1 + |f|)`. Бесконечности, NaN и переполнение при вычислении - ошибки.
