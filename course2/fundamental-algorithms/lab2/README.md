## Состав

| Задание | Исходный код | Тесты (`tests/`) | Входные данные (`tests/data/`) |
|---|---|---|---|
| 1 | `lab2_task1.c` | `tests_task1.txt` | - (аргументы командной строки) |
| 8 | `lab2_task8.c` | `tests_task8.txt` | - (без аргументов - демонстрация; иначе основание и числа) |

Каждое задание - один самостоятельный файл `.c`. В папке `drafts/` лежат черновики заданий, которые еще не приведены
к требованиям: они не собираются и не тестируются. Готовое задание переносится из `drafts/` в корень и добавляется в таблицу.

## Сборка и проверка

Программы собираются в папку `build/`.

```sh
make                              # gcc -std=c99 -Wall -Wextra -Wpedantic -g ... -lm  ->  build/lab2_taskN
make test                         # все тесты
make memcheck                     # все тесты под valgrind
bash run_tests.sh 1               # тесты одного задания
bash run_tests.sh --memcheck 1    # то же под valgrind
./build/lab2_task1 -r hello       # запуск одной программы
make clean                        # удалить build/
```

Файл тестов (`tests/tests_taskN.txt`): первая значимая строка `program: <имя>`, далее блоки, разделенные пустой строкой.
Поля блока: `args` (аргументы; аргумент с пробелами - в кавычках), `input` (строка стандартного ввода),
`out` / `outre` (строка stdout; `outre` - регулярное выражение POSIX ERE), `err` (строка stderr), `code` (код возврата),
`file` / `fout` (файл, который должна создать программа, и его строки). Строки сравниваются целиком, без учета пробелов в конце.
Пути в тестах (`tests/data/...`) указаны относительно корня репозитория: `run_tests.sh` запускает программы из него.

## Проверка утечек и ошибок памяти

`make memcheck` запускает каждый тест из `tests/tests_task*.txt` (включая ветви с ошибочным вводом) под

```sh
valgrind -q --leak-check=full --show-leak-kinds=definite,indirect,possible \
         --errors-for-leak-kinds=definite,indirect,possible --track-origins=yes --error-exitcode=99
```

Тест считается непройденным, если valgrind завершился с кодом 99 (ошибка доступа к памяти или утечка); в конце выводится итог по каждому заданию.

Результат проверки (Ubuntu в WSL 2, gcc 15.2.0, valgrind 3.26.0): сборка с `-Werror` без предупреждений, все тесты пройдены,
valgrind - 0 ошибок и 0 утечек. Та же проверка выполняется GitHub Actions при каждом push (`.github/workflows/check.yml`).
На Windows (сборка `zig cc`, Universal CRT) те же тесты проходят; утечки дополнительно проверены Dr. Memory 2.6.0 и heob 4.2.

## Замечания по заданиям

**Задание 1, флаг `-c`.** По условию генератор засевается функцией `srand`, поэтому используется стандартная пара
`srand`/`rand`. Формула `rand` в стандарте не задана: при одном и том же seed порядок склейки на Linux (glibc) и
Windows (UCRT) различается, а на одной системе всегда повторяется. Поэтому тесты проверяют результат `-c`
регулярным выражением (любая перестановка строк). Строки обрабатываются побайтно (`char`): для текста в UTF-8
длина `-l` - это число байт.

**Задание 8.** Числа хранятся строками и складываются поразрядно (`add_in_base`), поэтому их длина не ограничена
встроенными типами. Функция с переменным числом аргументов `sum_in_base(&rez, base, kolvo, ...)` принимает числа
как `char *`. При запуске с аргументами командной строки числа прибавляются к сумме по одному
(`sum_in_base(&rez, base, 2, summa, argv[i])`), так как количество аргументов `...` должно быть известно при компиляции.
На входе цифры-буквы допускаются в любом регистре, в ответе - заглавные; ведущие нули удаляются.
